# 0006 — DOM-render вместо Canvas-render

**Дата:** 2026-07-14
**Статус:** Принято

## Контекст

Нужно выбрать технологию рендеринга игровых сцен. Альтернативы: HTML DOM (через CSS/SVG) или Canvas 2D (через `<canvas>`).

## Решение

Использовать **DOM-render** для всех игровых сцен. Игровая сцена = набор HTML/SVG элементов с CSS-стилями и анимациями.

## Альтернативы

- **Canvas 2D** — одна большая `<canvas>`, рисование через API
- **WebGL** — 3D и сложные эффекты
- **Phaser** — обёртка над Canvas, добавляет зависимость
- **PixiJS** — рендерер для Canvas/WebGL с удобным API
- **Three.js** — 3D
- **DOM-render** — HTML + CSS + SVG

## Почему DOM, а не Canvas

1. **ИИ лучше пишет DOM-код.** Canvas требует знания API, transform, paths, sprites. DOM — это знакомый HTML.
2. **Отладка проще.** Можно открыть DevTools и увидеть каждый элемент. Canvas — это "чёрный ящик" с пикселями.
3. **CSS-анимации** бесплатны. Canvas нужно реализовывать самому (requestAnimationFrame + интерполяция).
4. **Адаптивность автоматическая.** Canvas нужно пересчитывать при resize. DOM через viewport units и media queries.
5. **Accessibility** — screen readers понимают DOM, не Canvas.
6. **Стили через CSS variables** — легко менять тему.

## Когда DOM НЕ подходит

- > 200 одновременно движущихся объектов (Canvas быстрее)
- 60 FPS обязателен (DOM имеет overhead)
- Эффекты вроде blur/glow/shader (CSS-фильтры нагружают)
- Большой мир с прокруткой (только видимая часть)

## Последствия

✅ Простая разработка
✅ Лёгкая отладка
✅ Адаптивность из коробки
✅ Бесплатные CSS-анимации
✅ Лучшая поддержка ИИ

❌ Ограничение на количество объектов
❌ Сложнее делать "тяжёлые" эффекты

## Когда пересмотреть

- Если потребуется 60 FPS с > 200 объектами
- Если понадобятся шейдерные эффекты
- Если Canvas/WebGL API станут проще для ИИ
