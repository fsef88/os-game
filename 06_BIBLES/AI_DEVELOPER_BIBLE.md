## 1. ЕДИНЫЙ СТЕК

### Технологии (не подлежат обсуждению)

```
HTML5       — TypeScript → компилируется в ES2020 JS
Bundler     — Vite
UI          — чистый DOM (НЕ React, НЕ Vue, НЕ Phaser)
Стили       — CSS с CSS variables
Хранилище   — localStorage + Yandex Player Data
SDK         — Yandex Games SDK v2 (скрипт-тегом)
Графика     — SVG inline (НЕ Canvas, НЕ WebGL для UI)
Анимации    — CSS animations + Web Animations API
Звук        — Web Audio API (опционально)
```

### Почему этот стек

- **DOM** — ИИ лучше всего пишет DOM-код. Canvas и Phaser требуют глубокой экспертизы, модель делает ошибки.
- **TypeScript** — типы ловят 80% ошибок до runtime.
- **Vite** — мгновенный dev-server, простая сборка в один HTML.
- **SVG** — масштабируется, весит мало, легко менять.
- **Без фреймворков** — минимум зависимостей = минимум точек отказа.

### Зависимости

Минимум. Только если без них никак:

```json
{
  "dependencies": {},
  "devDependencies": {
    "typescript": "^5.0.0",
    "vite": "^5.0.0"
  }
}
```

Если ИИ предлагает React/Vue/Phaser — отклонить без обсуждения.

### Правила именования

- Файлы: `kebab-case.ts`
- Классы: `PascalCase`
- Функции/переменные: `camelCase`
- Константы: `UPPER_SNAKE_CASE`
- CSS-классы: `kebab-case` (соответствуют BEM-лайт)

### Максимальный размер файла

- **300 строк** — мягкий лимит
- **500 строк** — жёсткий лимит

### Максимальный размер функции

- **50 строк** — мягкий лимит
- **100 строк** — жёсткий лимит
- Если больше — разбить на подфункции

## 3. СТИЛЬ КОДА

### Приоритеты

```
1. Читаемость
2. Простота
3. Поддерживаемость
4. Производительность
```

### Правила

- ❌ Никаких `magic numbers` — выноси в `config.ts`
- ❌ Никакого дублирования кода — DRY
- ❌ Никаких `!important` в CSS (кроме viewport-обязательных)
- ❌ Никаких inline-стилей в HTML
- ❌ Никаких однострочных функций больше 80 символов
- ❌ Никаких "TODO" в коммитах — сразу делай
- ❌ Никаких console.log в релизе (используй analytics)

### Комментарии

- Над блоками логики — почему, а не что
- Перед сложными формулами — пример ввода/вывода
- Никаких "это делает X" — и так видно
- JSDoc для публичного API

Пример хорошего комментария:
```ts
// Рассчитываем оффлайн-доход: 50% от того, что заработал бы за это время,
// но не больше чем 3x от текущего максимального дохода за сессию.
// Это защищает от нечестных игроков, которые ставят телефон на ночь.
function calculateOfflineEarnings(elapsedSec: number): number {
```

Пример плохого:
```ts
// Считаем оффлайн
function calc(e: number): number {
```

### TypeScript

- `strict: true` в tsconfig
- Никаких `any` (используй `unknown` + type guard)
- `interface` для объектов, `type` для union/intersection
- Все публичные функции — с типами параметров и возврата

## 4. АРХИТЕКТУРНЫЕ ПРАВИЛА

### Архитектура: простой state + render

```ts
// state.ts — единый источник истины
export const state = {
  grid: [...],
  money: 0,
  level: 1,
  // ...
};

// Изменение ТОЛЬКО через мутации
export function addMoney(amount: number) {
  state.money += amount;
  notifyChange();  // подписчики перерисуют UI
}

// UI подписывается
onChange(() => {
  updateHud();
  updateGrid();
});
```

### Что ЗАПРЕЩЕНО

- ❌ Глобальные переменные кроме `state`
- ❌ Прямое изменение DOM из core-логики
- ❌ Бизнес-логика в UI-коде
- ❌ setTimeout/setInterval для геймплея без save/restore
- ❌ Math.random() в местах, где нужна воспроизводимость
- ❌ Мьютексы и блокировки (DOM однопоточный, не нужны)

### Что РАЗРЕШЕНО

- ✅ Один большой state + render
- ✅ Подписки на изменения
- ✅ Чистые функции для расчётов
- ✅ Async/await для SDK и сети
- ✅ Web Animations API для UI-эффектов

### Когда можно менять архитектуру

- ❌ Никогда "для красоты"
- ❌ Никогда "чтобы было современнее"
- ✅ Если текущая не решает задачу (сначала локальное решение!)
- ✅ Если производительность < 30 FPS из-за архитектуры
- ✅ Если добавляется новая обязательная система (IAP, мультиплеер)

## 5. РАБОТА С ИИ

### Контекст, который нужен ИИ при любой задаче

1. PROJECT_STATE.md
2. CURRENT_TASK.md
3. DECISIONS.md (последние 5 решений)
4. CHANGELOG.md (последние 10 изменений)
5. Затронутые файлы (не весь проект)

### Промпт-шаблон

```text
Роль: <Programmer | QA | Reviewer>

Задача: <что сделать, одним предложением>

Контекст:
- Что уже есть: <кратко>
- Чего не трогать: <список файлов/систем>
- Ограничения: <производительность, размер, сроки>

Definition of Done:
- <что должно работать после>

После выполнения:
1. Self Review
2. Обнови CHANGELOG.md
3. Обнови PROJECT_STATE.md
4. Если затронуты решения — обнови DECISIONS.md
```

### Что ИИ должен спросить ДО работы

- Непонятна задача
- Нужно менять архитектуру
- Затронуто > 5 файлов
- Затронут Save/Load
- Затронут SDK
- Затронут баланс

### Что ИИ НЕ должен спрашивать

- Очевидных вещей (используй config.ts)
- Стилевых решений (придерживайся UI_UX_BIBLE)
- Архитектурных деталей (придерживайся AI_DEVELOPER_BIBLE)

### После каждой задачи ИИ даёт отчёт

```text
Что изменено: <список файлов>
Почему: <обоснование>
Scope: <LOW | MEDIUM | HIGH | CRITICAL>
Риски: <что может сломаться>
Что проверить: <конкретные действия>
```

## 6. ТИПИЧНЫЕ ОШИБКИ ИИ (и как их избежать)

### Scope Explosion
"Исправить кнопку" → рефакторинг всего UI  
**Лечение:** изменять минимум. Если задача LOW, она должна остаться LOW.

### Architecture Addiction
ИИ видит 100 строк — сразу "надо переписать"  
**Лечение:** "Пока работает — не трогать". Рефакторинг — только по запросу.

### Future Programming
"А вдруг потом пригодится..."  
**Лечение:** делать для сегодняшней задачи. YAGNI.

### Magic Refactor  
"Я заодно почистил архитектуру"  
**Лечение:** никаких "заодно". Каждая задача — атомарна.

### Hallucinated Requirements
ИИ придумал требования, которых не было  
**Лечение:** перечитать задачу. Если "чего-то нет" — спросить.

### Premature Optimization
"Я оптимизирую на всякий случай"  
**Лечение:** оптимизировать только если есть профилирование.

### Unrequested Help
ИИ добавляет "полезные" фичи  
**Лечение:** строго по Definition of Done.

## 7. САМОПРОВЕРКА ИИ (SELF REVIEW)

После каждой задачи ИИ отвечает на 7 вопросов:

1. Сделал ли я ровно то, что просили?
2. Добавил ли я что-то от себя? → Убрать.
3. Изменил ли я архитектуру? → Объяснить.
4. Можно ли было изменить меньше файлов?
5. Что может сломаться?
6. Нужно ли обновить документацию?
7. Нужно ли обновить CHANGELOG?

Если хотя бы на один вопрос "не знаю" — задача не завершена.
